# Requirements Document

## Introduction

Pear'd currently ships an Expo (React Native) iOS app in `app/`, with a prebuilt
`app/ios/` Xcode project generated by `expo prebuild` and a WidgetKit extension
generated by `@bacons/apple-targets`. This feature replaces that app layer with a
hand-maintained native SwiftUI iOS application.

The PocketBase Go server (`server/`) is unchanged: the SwiftUI app talks to the
same PocketBase REST collections and the same custom `/api/peard/*` routes. The
wire contract currently described by `shared/types.ts` becomes a set of Swift
`Codable` models owned by the iOS app.

Scope covers: feature parity with the existing React Native app, the WidgetKit
extension moving from a generated target to a first-class target in a
hand-maintained Xcode project, replacing the `PearShared` Expo native module with
in-process App Group access, closing two gaps that exist in the React Native app
today (APNs device registration is never performed, and reactions exist on the
server with no client UI), the decommissioning path for the Expo project and the
prebuilt `app/ios/` directory, and an explicit decision on the Android target
that the README currently describes as sharing the React Native codebase.

Behaviour was captured from `app/App.tsx`, `app/src/**`, `app/app.json`,
`app/targets/pear-widget/index.swift`, `app/modules/pear-shared/ios/PearSharedModule.swift`,
and the server packages `internal/auth`, `internal/pairs`, `internal/widget`,
`internal/push` plus `migrations/1785110400_peard_init.go`.

## Glossary

- **Peard_App**: The new native SwiftUI iOS application that replaces the Expo (React Native) app.
- **Legacy_App**: The existing Expo (React Native) application in `app/`, including the prebuilt `app/ios/` Xcode project and the `PearShared` Expo native module.
- **Peard_Server**: The PocketBase-as-a-framework Go server in `server/`, exposing PocketBase collection REST endpoints and the custom `/api/peard/*` routes.
- **Pear_Widget**: The WidgetKit extension that renders the partner's latest post and today's tallies on the home screen.
- **Peard_Core**: The shared Swift module containing domain models, the API client, and App Group access, linked by both Peard_App and Pear_Widget.
- **API_Client**: The component of Peard_Core that performs HTTP requests against Peard_Server and decodes responses.
- **Domain_Models**: The Swift `Codable` types in Peard_Core that mirror the wire contract previously declared in `shared/types.ts`.
- **Session_Store**: The component of Peard_App that persists the PocketBase auth token and the signed-in user id in the iOS Keychain.
- **Shared_Store**: The component of Peard_Core that reads and writes the App Group container `group.com.peard.app` via `UserDefaults(suiteName:)`.
- **Auth_Coordinator**: The component of Peard_App that performs Sign in with Apple and Sign in with Google and reports the resulting PocketBase token and user record.
- **Pair_Coordinator**: The component of Peard_App that calls `/api/peard/pairs/invite`, `/api/peard/pairs/accept`, and `/api/peard/pairs/leave`.
- **Push_Coordinator**: The component of Peard_App that requests notification authorization, registers the APNs device token with Peard_Server, and handles received notifications.
- **Widget_Sync**: The component of Peard_App that issues a widget token from `/api/peard/widget/token`, writes it to Shared_Store, and asks WidgetKit to reload timelines.
- **Deep_Link_Router**: The component of Peard_App that resolves incoming `peard://` URLs to an app destination.
- **Post**: A record in the PocketBase `posts` collection, of type `photo` or `event`.
- **Event_Kind**: The tally category of an `event` Post; the Peard_App set is `beer`, `loo`, and `coffee`.
- **Reaction**: A record in the PocketBase `reactions` collection with kind `cheers`, `plus_one`, or `heart`.
- **Widget_Token**: The revocable token issued by `POST /api/peard/widget/token`, stored in the App Group container and used as the `token` query parameter of `GET /api/peard/widget/feed`.
- **Pair_Phase**: The top-level Peard_App state, one of `loading`, `auth`, `pair`, or `home`.
- **Wire_Contract_Document**: The single document that records the JSON shapes exchanged between Peard_App and Peard_Server, replacing `shared/types.ts` as the canonical description.
- **Debug_Build**: A build of Peard_App produced with the `DEBUG` compilation condition active.

## Requirements

### Requirement 1: Xcode Project and Target Layout

**User Story:** As the maintainer, I want a hand-maintained Xcode project with app, widget, and shared targets, so that I can build the iOS app without Expo prebuild or CocoaPods.

#### Acceptance Criteria

1. THE Peard_App SHALL build from an Xcode project that is committed to the repository and regenerated by no code-generation step.
2. THE Peard_App SHALL declare exactly three first-party targets: the SwiftUI application, the Pear_Widget widget extension, and the Peard_Core shared module.
3. THE Peard_App SHALL link Peard_Core into both the application target and the Pear_Widget target.
4. THE Peard_App SHALL build with `xcodebuild` using only Swift Package Manager dependencies and system frameworks.
5. THE Peard_App SHALL exclude every React Native, Expo, CocoaPods, and Node.js runtime dependency from its build inputs.
6. THE Peard_App SHALL set a minimum deployment target of iOS 17.0.
7. THE Peard_App SHALL declare the bundle identifier `com.peard.app` and the Apple Developer team identifier `72Q6R744M4`.
8. THE Pear_Widget SHALL declare a bundle identifier prefixed by `com.peard.app.`.

### Requirement 2: Capabilities, Entitlements, and Info.plist Parity

**User Story:** As the maintainer, I want the native project to declare the same capabilities the Expo config produced, so that Apple sign-in, App Group sharing, push, camera, and deep links keep working.

#### Acceptance Criteria

1. THE Peard_App SHALL declare the App Group `group.com.peard.app` in the entitlements of both the application target and the Pear_Widget target.
2. THE Peard_App SHALL declare the Sign in with Apple capability in the application target entitlements.
3. THE Peard_App SHALL declare the `aps-environment` entitlement, set to `development` for Debug configurations and `production` for Release configurations.
4. THE Peard_App SHALL declare the `remote-notification` and `fetch` background modes.
5. THE Peard_App SHALL declare `NSCameraUsageDescription` with the text "Take a photo to share a moment with your partner."
6. THE Peard_App SHALL declare `NSPhotoLibraryUsageDescription` with the text "Pick a photo to share with your partner."
7. THE Peard_App SHALL register the URL scheme `peard`.
8. THE Peard_App SHALL declare the supported interface orientation set as portrait only.
9. THE Peard_App SHALL declare iPhone and iPad as supported device families.
10. THE Peard_App SHALL declare a privacy manifest that lists the same required-reason API categories as `app/ios/Peard/PrivacyInfo.xcprivacy`.

### Requirement 3: Runtime Configuration

**User Story:** As the maintainer, I want the server URL and Google client id configurable per build, so that I can point a device build at a LAN server without editing source.

#### Acceptance Criteria

1. THE Peard_App SHALL read the Peard_Server base URL from a build configuration value that is resolvable at launch.
2. IF the configured Peard_Server base URL is absent, THEN THE Peard_App SHALL use `http://127.0.0.1:8090`.
3. THE Peard_App SHALL read the Google iOS OAuth client identifier from a build configuration value.
4. IF the Google iOS OAuth client identifier is an empty string WHEN the user starts Sign in with Google, THEN THE Peard_App SHALL display the message "Set the Google iOS client id in the build configuration first" and cancel the sign-in attempt.
5. THE Peard_App SHALL exclude the resolved configuration values from source control by reading them from a git-ignored configuration file with a committed example counterpart.
6. WHERE the build configuration is Debug, THE Peard_App SHALL permit cleartext HTTP requests to the configured Peard_Server host.

### Requirement 4: Swift Domain Models Replacing the Shared TypeScript Types

**User Story:** As the maintainer, I want Swift models that mirror the server's JSON, so that the TypeScript type boundary can be retired without losing the contract.

#### Acceptance Criteria

1. THE Domain_Models SHALL define a `Post` type carrying `id`, `pair`, `author`, `type`, `event_kind`, `note`, `media`, and `created`.
2. THE Domain_Models SHALL define a `WidgetFeed` type carrying `state`, `partner`, `counts`, and `post`, where `state` is one of `ok`, `empty`, or `unpaired`.
3. THE Domain_Models SHALL define a `PairInvite` type carrying `code`, `expires`, and `deep_link`.
4. THE Domain_Models SHALL define a `PairMember` type carrying `pair`, `user`, and `role`, where `role` is one of `owner` or `member`.
5. THE Domain_Models SHALL define a `Reaction` type carrying `post`, `user`, and `kind`, where `kind` is one of `cheers`, `plus_one`, or `heart`.
6. THE Domain_Models SHALL define the Event_Kind catalogue as the ordered list `beer` with emoji 🍺 and label "Beer", `loo` with emoji 💩 and label "Loo", and `coffee` with emoji ☕ and label "Coffee".
7. WHEN a JSON payload contains a `type`, `state`, `role`, or `kind` value outside the enumerated set, THE Domain_Models SHALL decode the value into an unknown case that preserves the original string.
8. FOR ALL Domain_Models values, THE Domain_Models SHALL produce a value equal to the original when encoding then decoding then encoding the value (round-trip property).
9. THE Domain_Models SHALL decode PocketBase date strings of the form `yyyy-MM-dd HH:mm:ss.SSS'Z'` in the UTC time zone into `Date` values.
10. FOR ALL `Date` values expressible in the PocketBase date format, THE Domain_Models SHALL produce a `Date` equal to the original when formatting then parsing the value (round-trip property).
11. THE Wire_Contract_Document SHALL record every field name, type, and enumerated value listed in this requirement.
12. THE Wire_Contract_Document SHALL replace `shared/types.ts` as the canonical description of the client-server JSON contract.

### Requirement 5: API Client for PocketBase Collections

**User Story:** As a developer, I want a single typed API client, so that every screen reads and writes PocketBase records the same way.

#### Acceptance Criteria

1. THE API_Client SHALL send the stored PocketBase auth token in the `Authorization` header of every authenticated request.
2. WHEN a caller requests a record list, THE API_Client SHALL issue `GET /api/collections/{collection}/records` with `filter`, `sort`, and `perPage` query parameters.
3. WHEN a caller requests the first matching record, THE API_Client SHALL issue a list request with `perPage` equal to 1 and sort `-created`, and return the single record or no record.
4. WHEN a caller creates a record with a JSON body, THE API_Client SHALL issue `POST /api/collections/{collection}/records` with the `Content-Type` header set to `application/json`.
5. WHEN a caller creates a record with an image attachment, THE API_Client SHALL issue `POST /api/collections/posts/records` as a `multipart/form-data` request containing the `pair`, `author`, `type`, and `media` parts.
6. IF Peard_Server returns a response status outside the range 200 to 299, THEN THE API_Client SHALL return an error carrying the `message` field of the response body when that field is present, and the status code otherwise.
7. IF a request fails before a response is received, THEN THE API_Client SHALL return an error describing the transport failure.
8. WHEN a caller builds a filter containing a user-supplied value, THE API_Client SHALL escape the value so that the enclosing filter expression retains its original structure.
9. THE API_Client SHALL apply a request timeout of 30 seconds to every request.

### Requirement 6: Sign in with Apple

**User Story:** As a user, I want to sign in with my Apple ID using the native dialog, so that I do not create another password.

#### Acceptance Criteria

1. WHEN the user selects Sign in with Apple, THE Auth_Coordinator SHALL present the system `AuthenticationServices` credential dialog requesting the full name and email scopes.
2. THE Auth_Coordinator SHALL generate a random raw nonce for each sign-in attempt and set the request nonce to the lowercase hexadecimal SHA-256 digest of that raw nonce.
3. WHEN the credential dialog returns an identity token, THE Auth_Coordinator SHALL issue `POST /api/peard/auth/apple` with the body fields `identity_token`, `nonce` set to the raw nonce, and `display_name`.
4. THE Auth_Coordinator SHALL set `display_name` to the given name and family name of the returned credential joined by a single space, omitting absent components.
5. WHEN `POST /api/peard/auth/apple` returns a success response, THE Auth_Coordinator SHALL report the `token` and `record` fields of the response body as the established session.
6. IF the credential dialog returns no identity token, THEN THE Auth_Coordinator SHALL report the message "Apple returned no identity token".
7. IF the user cancels the credential dialog, THEN THE Auth_Coordinator SHALL return to the sign-in screen with no error message displayed.
8. IF `POST /api/peard/auth/apple` returns an error response, THEN THE Auth_Coordinator SHALL display the `message` field of the response body.

### Requirement 7: Sign in with Google

**User Story:** As a user, I want to sign in with my Google account, so that I can use the account I already have.

#### Acceptance Criteria

1. WHEN the user selects Sign in with Google, THE Auth_Coordinator SHALL start an `ASWebAuthenticationSession` against `https://accounts.google.com/o/oauth2/v2/auth` requesting the scopes `openid`, `profile`, and `email` with response type `code`.
2. THE Auth_Coordinator SHALL use PKCE with an S256 code challenge derived from a per-attempt code verifier.
3. THE Auth_Coordinator SHALL use the redirect URI `peard://auth/google`.
4. WHEN the authorization session returns an authorization code, THE Auth_Coordinator SHALL issue `POST /api/collections/users/auth-with-oauth2` with the provider `google`, the returned code, the code verifier, and the redirect URI.
5. WHEN the OAuth2 code exchange returns a success response, THE Auth_Coordinator SHALL report the `token` and `record` fields of the response body as the established session.
6. IF the user dismisses the authorization session, THEN THE Auth_Coordinator SHALL return to the sign-in screen with no error message displayed.
7. IF the OAuth2 code exchange returns an error response, THEN THE Auth_Coordinator SHALL display the `message` field of the response body.

### Requirement 8: Session Persistence in the Keychain

**User Story:** As a user, I want to stay signed in between launches, so that I do not re-authenticate every time I open the app.

#### Acceptance Criteria

1. WHEN a session is established, THE Session_Store SHALL persist the PocketBase auth token and the signed-in user id to the iOS Keychain with the accessibility attribute `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`.
2. WHEN Peard_App launches, THE Session_Store SHALL load any persisted auth token and user id from the Keychain.
3. WHEN the user signs out, THE Session_Store SHALL delete the persisted auth token and user id from the Keychain.
4. IF an authenticated request returns status 401, THEN THE Peard_App SHALL clear the persisted session and set Pair_Phase to `auth`.
5. THE Session_Store SHALL store no auth token, user id, or Widget_Token in `UserDefaults.standard`.

### Requirement 9: Launch Routing and Phases

**User Story:** As a user, I want the app to open on the right screen for my state, so that I reach my shared timeline without extra taps.

#### Acceptance Criteria

1. WHEN Peard_App launches, THE Peard_App SHALL set Pair_Phase to `loading` and display a progress indicator.
2. IF no persisted auth token exists WHEN Peard_App resolves the launch phase, THEN THE Peard_App SHALL set Pair_Phase to `auth`.
3. WHILE a persisted auth token exists, THE Peard_App SHALL resolve pair membership by requesting the first `pair_members` record filtered by the signed-in user id.
4. WHEN pair membership resolution returns a record, THE Peard_App SHALL set Pair_Phase to `home` for the `pair` value of that record.
5. WHEN pair membership resolution returns no record, THE Peard_App SHALL set Pair_Phase to `pair`.
6. IF pair membership resolution fails with a transport error, THEN THE Peard_App SHALL set Pair_Phase to `pair` and display a retry control.
7. WHEN a session is established, THE Peard_App SHALL resolve pair membership and set Pair_Phase from the result.
8. WHEN the user signs out, THE Peard_App SHALL set Pair_Phase to `auth`.

### Requirement 10: Pairing

**User Story:** As a user, I want to pair with my partner using a short code, so that we share one timeline.

#### Acceptance Criteria

1. WHEN the user requests an invite code, THE Pair_Coordinator SHALL issue `POST /api/peard/pairs/invite` and display the returned `code`.
2. WHILE an invite code is displayed, THE Peard_App SHALL offer a share action that shares the text "Pear up with me on Pear'd! Code: {code}" followed by the returned `deep_link`.
3. THE Peard_App SHALL accept a pairing code entry of exactly 6 characters, converting entered letters to upper case.
4. WHILE the entered pairing code is shorter than 6 characters, THE Peard_App SHALL disable the accept control.
5. WHEN the user submits a 6-character pairing code, THE Pair_Coordinator SHALL issue `POST /api/peard/pairs/accept` with the body field `code`.
6. WHEN `POST /api/peard/pairs/accept` returns a success response, THE Peard_App SHALL resolve pair membership and set Pair_Phase from the result.
7. IF `POST /api/peard/pairs/invite` or `POST /api/peard/pairs/accept` returns an error response, THEN THE Peard_App SHALL display the `message` field of the response body.
8. WHILE a pairing request is in flight, THE Peard_App SHALL display a progress indicator in place of the submitted control's label.

### Requirement 11: Shared Timeline Display

**User Story:** As a user, I want to see the latest moment and our recent activity, so that I know what my partner has been up to.

#### Acceptance Criteria

1. WHEN Pair_Phase becomes `home`, THE Peard_App SHALL request the 5 most recent `posts` records of the current pair sorted by `-created`.
2. THE Peard_App SHALL display the most recent Post in a card, showing the author label, the Post type or Event_Kind, and the `note` value when that value is a non-empty string.
3. WHERE the most recent Post has type `photo` and a non-empty `media` value, THE Peard_App SHALL display the image at `/api/files/posts/{id}/{media}?thumb=512x512`.
4. WHERE the most recent Post has type `event`, THE Peard_App SHALL display the emoji of the Post's Event_Kind, and 🍐 when the Event_Kind is outside the catalogue.
5. WHEN the current pair has no Post records, THE Peard_App SHALL display the text "No moments yet — send a pear!".
6. THE Peard_App SHALL label a Post authored by the signed-in user "You" and a Post authored by the other member with that member's display name.
7. THE Peard_App SHALL derive the partner label from the `display_name` field of the partner's user record, from the local part of the partner's email when `display_name` is empty, and "Partner" when both are empty.
8. THE Peard_App SHALL truncate a displayed partner label longer than 8 characters to its first 7 characters followed by an ellipsis.
9. THE Peard_App SHALL display the 3 Post records that follow the most recent Post as a history list, each showing the author label, the type or Event_Kind emoji, the `note` value, and an elapsed-time label.
10. THE Peard_App SHALL render the elapsed-time label as "now" below 1 minute, whole minutes with suffix "m" below 60 minutes, whole hours with suffix "h" below 24 hours, and whole days with suffix "d" thereafter.
11. WHEN the user performs a pull-to-refresh gesture, THE Peard_App SHALL re-request the pair's posts and recompute the tallies.
12. WHILE Pair_Phase is `home` and Peard_App is in the foreground, THE Peard_App SHALL re-request the pair's posts and recompute the tallies every 30 seconds.
13. WHEN Peard_App returns to the foreground WHILE Pair_Phase is `home`, THE Peard_App SHALL re-request the pair's posts and recompute the tallies.

### Requirement 12: Event Tallies

**User Story:** As a user, I want to log a tally in one tap and see our counts, so that we can keep score of the small stuff.

#### Acceptance Criteria

1. THE Peard_App SHALL display one tally control per Event_Kind in the catalogue, showing that kind's emoji and label.
2. WHEN the user selects a tally control, THE Peard_App SHALL present an optional note field with the placeholder "Add a note (optional)…" and focus that field.
3. WHEN the user submits a tally, THE Peard_App SHALL create a `posts` record with `pair` set to the current pair, `author` set to the signed-in user, `type` set to `event`, `event_kind` set to the selected kind, and `note` set to the entered text.
4. WHEN a tally creation succeeds, THE Peard_App SHALL display the selected kind's emoji followed by " logged!" for 1.5 seconds, then remove that message.
5. WHEN a tally creation succeeds, THE Peard_App SHALL re-request the pair's posts, recompute the tallies, and ask WidgetKit to reload timelines.
6. WHEN the user dismisses the note field without submitting, THE Peard_App SHALL discard the entered text and leave the tally uncreated.
7. IF a tally creation returns an error, THEN THE Peard_App SHALL display an alert titled "Couldn't log it" carrying the error description.
8. THE Peard_App SHALL compute, for the signed-in user and for the partner separately, the count of `event` Post records created since the start of the current day, since the start of the current week beginning on Monday, since the start of the current month, and over all time.
9. THE Peard_App SHALL display both tally rows with the labels "You" and the partner label, each followed by the day, week, month, and all-time counts.
10. WHILE a tally creation is in flight, THE Peard_App SHALL disable every tally control and the photo capture control.

### Requirement 13: Photo Moments

**User Story:** As a user, I want to take a photo and send it to my partner, so that we share a moment instantly.

#### Acceptance Criteria

1. WHEN the user selects the photo capture control, THE Peard_App SHALL request camera authorization when the current authorization state is undetermined.
2. IF camera authorization is denied WHEN the user selects the photo capture control, THEN THE Peard_App SHALL display an alert titled "Camera access needed" with the body "Enable camera access in Settings to share a moment." and take no capture action.
3. WHILE camera authorization is granted, THE Peard_App SHALL present a camera capture interface offering a square crop.
4. WHEN the user confirms a captured image, THE Peard_App SHALL encode the image as JPEG with a compression quality of 0.6.
5. WHEN the encoded image is ready, THE Peard_App SHALL create a `posts` record as a multipart request with `type` set to `photo` and the image attached to the `media` part with the filename `pear.jpg` and the MIME type `image/jpeg`.
6. WHEN the photo upload succeeds, THE Peard_App SHALL re-request the pair's posts and ask WidgetKit to reload timelines.
7. WHEN the user cancels the camera capture interface, THE Peard_App SHALL create no `posts` record.
8. IF the photo upload returns an error, THEN THE Peard_App SHALL display an alert titled "Upload failed" carrying the error description.
9. WHILE a photo upload is in flight, THE Peard_App SHALL display a progress indicator in the photo capture control.

### Requirement 14: Reactions

**User Story:** As a user, I want to react to my partner's post, so that they know I saw it.

#### Acceptance Criteria

1. WHERE the displayed Post was authored by the partner, THE Peard_App SHALL offer one reaction control per Reaction kind, using 🍻 for `cheers`, 👏 for `plus_one`, and ❤️ for `heart`.
2. WHEN the user selects a reaction control, THE Peard_App SHALL create a `reactions` record with `post` set to the displayed Post, `user` set to the signed-in user, and `kind` set to the selected kind.
3. THE Peard_App SHALL display the reaction kinds already recorded against the displayed Post.
4. IF a reaction creation returns status 400 because the same reaction already exists, THEN THE Peard_App SHALL display the existing reaction as recorded and display no error message.
5. IF a reaction creation returns any other error response, THEN THE Peard_App SHALL display the `message` field of the response body.

### Requirement 15: Leaving a Pair and Signing Out

**User Story:** As a user, I want to unpair or sign out deliberately, so that I do not lose our timeline by accident.

#### Acceptance Criteria

1. WHEN the user selects the unpair control, THE Peard_App SHALL present a confirmation titled "Un-pear?" with the body "You'll both lose the shared timeline." offering a cancelling choice and a destructive choice.
2. WHEN the user confirms the destructive choice, THE Pair_Coordinator SHALL issue `POST /api/peard/pairs/leave` and then resolve pair membership and set Pair_Phase from the result.
3. IF `POST /api/peard/pairs/leave` returns an error response, THEN THE Peard_App SHALL resolve pair membership, set Pair_Phase from the result, and display the `message` field of the response body.
4. WHEN the user selects the sign-out control, THE Peard_App SHALL clear the persisted session, remove the Widget_Token from Shared_Store, delete the device registration, and set Pair_Phase to `auth`.

### Requirement 16: Widget Credential Sync

**User Story:** As a user, I want my home-screen widget to work right after I sign in, so that I see my partner's latest moment without opening the app.

#### Acceptance Criteria

1. WHEN a session is established, THE Widget_Sync SHALL issue `POST /api/peard/widget/token`.
2. WHEN `POST /api/peard/widget/token` returns a success response, THE Widget_Sync SHALL write the `token` value to Shared_Store under the key `widgetToken` and the Peard_Server base URL under the key `apiBaseUrl`, then ask WidgetKit to reload all timelines.
3. IF `POST /api/peard/widget/token` returns an error response, THEN THE Widget_Sync SHALL leave Shared_Store unchanged and allow the current session to continue.
4. WHEN the user signs out, THE Widget_Sync SHALL remove the `widgetToken` key from Shared_Store and ask WidgetKit to reload all timelines.
5. THE Widget_Sync SHALL access the App Group container directly through Peard_Core, replacing the `PearShared` Expo native module.

### Requirement 17: WidgetKit Extension

**User Story:** As a user, I want the home-screen widget to keep showing my partner's latest moment and today's tallies, so that the migration changes nothing I can see.

#### Acceptance Criteria

1. THE Pear_Widget SHALL support the `systemSmall` and `systemMedium` widget families.
2. THE Pear_Widget SHALL present the configuration display name "Pear'd" and the description "Your partner's latest moment and today's tallies.".
3. WHEN WidgetKit requests a timeline, THE Pear_Widget SHALL read `widgetToken` and `apiBaseUrl` from Shared_Store and request `GET /api/peard/widget/feed` with the token as the `token` query parameter.
4. IF `widgetToken` or `apiBaseUrl` is absent from Shared_Store, THEN THE Pear_Widget SHALL render the placeholder entry.
5. IF the widget feed request fails or returns an undecodable body, THEN THE Pear_Widget SHALL render the placeholder entry.
6. WHEN the widget feed returns state `unpaired`, THE Pear_Widget SHALL display the text "🍐 Pear up to get started".
7. WHEN the widget feed returns state `empty`, THE Pear_Widget SHALL display the text "Waiting for {partner name}'s first pear…".
8. WHERE the widget feed carries a non-empty `media_url`, THE Pear_Widget SHALL display the fetched image with the partner name and today's tally counts overlaid.
9. WHERE the widget feed carries an empty `media_url`, THE Pear_Widget SHALL display the Event_Kind emoji, the `note` value when non-empty, today's tally counts, and a relative time derived from `created`.
10. THE Pear_Widget SHALL display today's tally counts as the beer count and the loo count from the widget feed `counts` object.
11. WHEN WidgetKit requests a timeline, THE Pear_Widget SHALL return a refresh policy scheduling the next reload 15 minutes after the entry date.
12. THE Pear_Widget SHALL set its widget URL to `peard://home`.
13. THE Pear_Widget SHALL decode the widget feed using the Domain_Models `WidgetFeed` type from Peard_Core.

### Requirement 18: Push Notifications

**User Story:** As a user, I want to be notified when my partner posts or reacts, so that I can respond while it is still fresh.

#### Acceptance Criteria

1. WHEN Pair_Phase becomes `home` for the first time in a session, THE Push_Coordinator SHALL request notification authorization for alerts, sounds, and badges.
2. WHILE notification authorization is granted, THE Push_Coordinator SHALL register with APNs for remote notifications.
3. WHEN APNs returns a device token, THE Push_Coordinator SHALL create or update a `devices` record with `user` set to the signed-in user, `platform` set to `ios`, and `push_token` set to the lowercase hexadecimal representation of the device token.
4. IF a `devices` record already exists for the same `push_token`, THEN THE Push_Coordinator SHALL update that record rather than create a second record.
5. WHEN the user signs out, THE Push_Coordinator SHALL delete the `devices` record holding the current device token.
6. WHEN Peard_App receives a background notification carrying `content-available`, THE Push_Coordinator SHALL re-request the pair's posts, refresh Shared_Store, and ask WidgetKit to reload all timelines.
7. WHEN the user opens Peard_App by selecting a notification carrying a `post_id` value, THE Peard_App SHALL set Pair_Phase to `home` and display the Post identified by that value.
8. IF notification authorization is denied, THEN THE Peard_App SHALL continue to operate every feature that does not depend on remote notifications.
9. THE Push_Coordinator SHALL request notification authorization no more than once per installation unless the user selects a control that asks for notifications.

### Requirement 19: Deep Links

**User Story:** As a user, I want an invite link and my widget to open the right place in the app, so that pairing and browsing take one tap.

#### Acceptance Criteria

1. WHEN Peard_App opens a URL of the form `peard://pair/{code}`, THE Deep_Link_Router SHALL set Pair_Phase to `pair` and pre-fill the pairing code field with `{code}` in upper case.
2. WHEN Peard_App opens the URL `peard://home` WHILE a pair membership exists, THE Deep_Link_Router SHALL set Pair_Phase to `home`.
3. WHEN Peard_App opens the URL `peard://home` WHILE no pair membership exists, THE Deep_Link_Router SHALL set Pair_Phase to `pair`.
4. WHEN Peard_App opens a URL of the form `peard://auth/google`, THE Deep_Link_Router SHALL deliver the URL to the pending authorization session.
5. IF Peard_App opens a `peard://` URL matching no known route, THEN THE Deep_Link_Router SHALL leave Pair_Phase unchanged.
